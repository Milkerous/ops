# 决策记录

背景与约束：在 C/C++ 的增量构建中，Makefile 通常依赖开发者手动维护头文件关系。如果漏写或写错（导致 MD/RD），修改头文件时可能导致增量编译错误。本次实验的约束是：必须在保证构建正确性的前提下，尽量复用历史依赖图，避免每次全量分析造成过大的性能开销。依赖图的缓存不能错误复用，必须满足编译配置和代码内容的一致性。
选择与替代方案：采用基于“真实读取图（BuildChecker/GCC）”与“声明图（Makefile）”分离的机制。通过计算目标文件的编译配置（如 CFLAGS）、预处理结构（如 include 的哈希）作为缓存身份（Key）。当源文件内部实现（body）改变，但 include 结构和编译配置不变时，复用历史图；当 include 结构（包括间接 include）或 flags 发生改变时，强制刷新目标。
替代方案：采用单一的全量扫描，或者仅基于文件修改时间（mtime）来判断。全量扫描性能差，而单纯依赖 mtime 无法发现间接依赖的变更（例如头文件里加了 include），安全性不足。
A：缓存何时失效、配置身份如何绑定；B：共享变量怎样处理、失败怎样保证原目录不变。
代价与覆盖范围：引入增量扫描逻辑增加了代码复杂度；在极小的单文件项目中，增量扫描（包含 Git 状态检查、哈希计算）的耗时可能略高于或持平于全量扫描（如 E10 性能对比所示）。
覆盖范围：验证并覆盖了 6 类场景：unchanged（无变化）、body（普通代码变化）、include（新增直接依赖）、declaration（修改 Makefile 声明）、flags（编译选项变化）、header（间接头文件变化）。在各类场景下，增量扫描得出的 `actual`、`declared`、`findings` 集合与全量扫描结果完全一致。
验证命令与实际证据：运行 30 次增量与全量对比测试脚本（6类场景 × 5次重复）。
